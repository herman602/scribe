# Scribe v0.1.0 local release audit

Date: 2026-11-16  
Scope: local evidence only; no GitHub or Cloudflare state changed  
Runtime baseline: Python 3.14.5, uv 0.10.9, migration `0022`

## Result

The current source is suitable for private GitHub staging after its final local
gate. It is not yet a published release. Live Gmail authorization was excluded
on purpose: every public installation must bring its own Google Desktop OAuth
client, and CI must never depend on a real mailbox.

## History and secret review

The official Gitleaks 8.30.1 macOS arm64 archive was checked against its
published checksum before execution. The scan shape was:

```text
gitleaks detect --source . --config .gitleaks.toml --redact --verbose --log-opts=--all
```

The private development graph contained 141 reachable commits at the final
pre-audit scan. Gitleaks reported one redacted `generic-api-key` match. Manual
review showed that it was a synthetic ledger idempotency key in a test, not a
credential; the current fixture is operator-neutral.

The same history also contains pre-release author metadata tied to a private
work identity. That metadata is unnecessary for users and must not be
published. Deleting files from the tip would not remove it. The release policy
is therefore:

1. export the verified tracked tree;
2. initialize a new repository with one root commit and a public-safe author;
3. scan every commit in that new repository without `.gitleaksignore` or a
   path allowlist;
4. push only that root and subsequent public-release commits.

A rehearsal root commit containing 375 tracked files was created from the
verified tree. Gitleaks scanned its single commit and approximately 4.90 MB of
content: 0 findings. No raw scan report is stored in the repository.

## Fresh-clone rehearsal

A separate clone of the one-commit candidate contained no ignored files from
the working installation. The following user path was exercised:

| Step | Evidence |
| --- | --- |
| Dependency setup | `uv sync --extra dev` installed the locked environment and built `scribe-local==0.1.0`. |
| Initialization | `python -m app init` created private paths and migrated an empty SQLite database to `0022`. |
| Diagnostics before OAuth | Python, config, data directory, SQLite integrity, and migration checks passed; OAuth credentials/token were the only failures and the network check was skipped. |
| Synthetic OAuth validation | A non-routable fixture Desktop-client document passed shape validation at mode `0600`; token remained intentionally absent. |
| Gmail and parser behavior | 62 mocked full-sync, incremental-sync, bank-parser, and transaction-parsing tests passed. |
| Service generation | 11 integration/CLI tests passed against a fake launchd gateway; no user LaunchAgent was installed. |
| Backup | Online backup reported `revision=0022 integrity=ok foreign_key_violations=0 verified=True`. |
| Restore | Preview wrote nothing; confirmed restore completed at `0022` and retained a rollback copy. |
| Missing-token sync | Failed with the documented authorization instruction and persisted the dashboard warning without creating or exposing a token. |
| Offline dashboard | First-run home, cards, sync, and account pages returned HTTP 200 on loopback. |

The rehearsal caught one documentation defect: the Gmail OAuth guide did not
say that a downloaded `credentials.json` should be mode `0600`, while `doctor`
correctly warned about it. A regression assertion and the missing instruction
were added in commit `44550de`; the synthetic file then passed the credentials
check, leaving only the expected missing-token result.

## Formal-installation isolation

The rehearsal used only temporary directories and a loopback port. It did not
read or write the formal SQLite database, OAuth files, Keychain values, local
LaunchAgents, Cloudflare configuration, or the private Scribe hostname. The
existing service was not stopped or restarted.

The verified build produced a wheel and source distribution in a temporary
directory. Their final release hashes are intentionally not embedded here:
adding a hash to a file inside the source distribution would change that
distribution. Hashes will instead be computed after the private-staging commit
is frozen and presented out of band before tagging.

Remote workflow URLs, rendered GitHub checks, the final one-commit public root,
and release-asset hashes belong to the later private-staging gate.
